백업

두 앱의 백업은 서로 따로입니다. 지금은 앱 백업이 모두 같은 서버 디스크에만 있고, 출시 직후 Google Drive로 매일 올리는 것(A)을 붙입니다. 위키는 앱 백업과 별개로 Mac에서 GitHub으로 올라갑니다(위키).

무엇언제보관들어가는 것
anotar 자동 백업매일 정해진 시각(한국시간). 기본값은 꺼짐이라 백업 화면에서 켭니다. 화면의 '지금 백업'도 같은 방식최근 성공한 것 N개(1–60, 기본 7). 오래된 것은 앱이 지움SQLite 온라인 스냅샷, 첨부 파일, 공유 링크가 있으면 공유 링크 키. manifest.json에 체크섬을 적고, 만든 뒤 바로 검증합니다(server/backups.mjs)
anotar 배포 직전 백업자동 배포가 새 컨테이너로 바꾸기 직전, 매번지우지 않음. 배포할 때마다 하나씩 쌓임
anotar 수동 백업npm run backup -- create | verify | restore직접 관리
harukan매일 04:30 (systemd timer)7일 지나면 지움SQLite 파일 하나, 만든 뒤 quick_check
Google Drive (계획 A)매일, 두 앱 백업이 끝난 뒤서버보다 길게 (예: 매일 30개 + 매달 1개)위 두 백업 폴더를 rclone crypt로 암호화해 복사. 권한은 rclone이 만든 파일만 보는 drive.file
위키 원본daily.sh를 돌릴 때마다 끝에 pushgit 기록 전체wiki/, sessions/ Markdown → 비공개 repo memory-data

백업에 없는 것

  • 서버 .env의 AUTH_SECRET_KEY. 로그인용 TOTP 비밀값은 이 키로 암호화돼 DB에 들어갑니다. 백업만 있고 키가 없으면 복원한 DB로 로그인할 수 없습니다. 키는 백업과 따로, 서버 밖에도 보관합니다.
  • 정적 호스팅 사이트 파일. DB와 다른 폴더에 있고 따로 백업하지 않습니다.
  • 공유 서버가 읽는 공개 폴더(공유 스냅샷). 개인 DB에서 다시 만들어지는 사본입니다.

복원

restore는 비어 있는 새 폴더로만 풀고, 풀기 전과 후에 다시 검증합니다. 쓰던 데이터 폴더를 덮어쓰지 않으므로 서비스를 멈추고 폴더를 바꿔 끼우는 것은 사람이 합니다. 자동 백업 설정과 기록은 백업 폴더 쪽에 있어서, 데이터 폴더를 새로 시작해도 설정은 남습니다.

Google Drive 백업 (A) 붙이는 순서

  1. 서버에 rclone 설치. Google 로그인은 서버에서 브라우저를 열 수 없으므로 Mac에서 rclone authorize "drive"로 받은 토큰을 서버 설정(root만 읽는 파일)에 넣습니다.
  2. Drive 위에 crypt 저장소를 하나 더 만들어 파일 내용과 이름을 암호화합니다. 비밀번호는 비밀번호 관리자에만 둡니다.
  3. systemd timer가 매일 두 백업 폴더 중 새것을 올리고, Drive 쪽 보관 개수를 정리합니다.
  4. 처음 한 번은 Drive에서 받아 verify와 restore까지 해 봅니다. 복원이 안 되는 백업은 백업이 아닙니다.
아직 없는 것: Google Drive 사본과 정기 복원 연습. 그 전까지는 출시 때 손으로 받아 둔 사본이 유일한 서버 밖 사본입니다. 배포 직전 백업은 쌓이기만 하므로 가끔 디스크 여유를 확인합니다.

AI 요청: 두 군데에서 나갑니다

AI를 부르는 곳은 서버와 Mac 두 군데이고, 서로 기록을 나누지 않습니다.

서버 (anotar)Mac (위키)
누가 시키나anotar 화면에서 요청 → 서버 큐 → 작업기가 순서대로 실행. 브라우저를 닫아도 계속됩니다daily.sh를 실행할 때
실행기Hive(모델 고정), OpenCode CLI(서버 이미지 안, 무료 모델 목록은 설정 › AI). 자동으로 다른 제공자로 바꾸지 않음claude, codex, opencode 중 하나
키·인증서버 .env(백업에 없음, 다시 넣으면 됨). 브라우저로는 키를 보내지 않음Mac의 각 CLI 로그인
기록개인 SQLite(ai_jobs 등) → 화면 /ai에서 보고, anotar 백업에 포함sessions/ 요약 → GitHub
위키에 들어가나아니요. 넣으려면 서버 기록을 가져오는 단계를 따로 만들어야 합니다네 (이것이 위키의 재료)

위키 (memory)

위키는 Mac에서 만들고, 서버는 다 만든 결과 파일을 보여 주기만 합니다. 서버는 위키를 고치거나 AI를 부르지 않습니다.

질문답
무엇이 위키에 들어가나이 Mac에서 쓴 AI 대화(Claude Code, Codex, opencode)의 요약이 'AI 기록'으로 쌓이고, 그중 고른 것만 '위키' 주제 페이지로 옮깁니다(규칙은 데이터 repo의 AGENTS.md).
안 들어가는 것anotar 서버의 AI 요청 기록(AI 요청)과 anotar 메모·페이지. 넣으려면 ①에 서버 기록을 가져오는 단계를 따로 만들어야 합니다.
AI 요약은 어디서Mac의 CLI(claude, codex, opencode)가 합니다. 모델은 daily.sh 인자로 고릅니다.
백업④ GitHub push가 곧 백업입니다. raw/sessions 덤프는 비밀값이 섞일 수 있어 git에 안 올리고 Mac에만 둡니다. 원래 기록(~/.claude 등)에서 다시 만들 수 있지만, 그 원래 기록도 도구가 오래된 것을 지울 수 있습니다.
운영에서 보려면⑤: Mac이 data.json을 SSH로 서버의 읽기 전용 폴더에 올립니다. 서버 코드는 이미 준비돼 있습니다(server/memoryData.mjs). 매일 자동 실행(Mac 예약)과 함께 출시 뒤에 붙입니다.

지금 운영 구성과 바뀔 구성

repo의 infra/에는 다음 구성이 이미 들어 있지만, 운영 서버는 아직 예전 구성입니다.

지금 운영repo의 다음 구성 (infra/)
개인 앱 주소anotar.leneu.store → 8787 바로 (위키 화면은 memory가 없어 아직 안 열림)anotar.leneu.store → Caddy(8780) → anotar·memory
개인 스택anotar 컨테이너 하나infra/personal: anotar + memory + Caddy, Caddy만 열림
공유 스택개인 데이터 폴더를 읽기 전용으로 붙임infra/public: 개인이 내보낸 공개 폴더만 읽음
harukan그대로: apps/harukan/compose.oracle.yaml, tunnel이 8794로 바로

이번 출시 순서(요약): tunnel에 새 주소 추가 → harukan 백업·새 버전 → 서버 배포 스크립트 갱신 → 개인 DB 백업을 서버 밖으로 받기 → main merge(자동 배포) → 개인 DB 새로 시작 → 자동 백업 켜기. infra/personal 스택으로 옮기는 것은 그 뒤 단계입니다. 자세한 절차와 확인 항목은 비공개 문서에 있습니다.
