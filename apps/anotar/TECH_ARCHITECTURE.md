# leneu 기술 아키텍처

작성: 2026-09-26
상태: 미니PC 운영까지의 목표 설계. **현재 실행되는 코드와 제한은 [현재 구현 규격](CURRENT_IMPLEMENTATION.md)을 기준으로 본다.** 메모 정리 완료/복귀·Page 출처·메모/Page AI·명시 반영과 제한된 되돌리기, Devin CLI·HTTP 게이트웨이 계약·로컬 읽기 전용 공유·일정 지도·페이지 도구·수정 이력·자동 백업을 구현했다. 본인 인증·실제 공개 주소 연결·별도 작업자/격리 서비스·N100 운영은 후속 목표다.

## 1. 실행 원칙

- 운영 장비는 **Intel N100, RAM 16GB, SSD 512GB** 미니PC다. 생성형 LLM 추론 서버를 상시 실행하는 구성은 기본값으로 잡지 않는다. 작은 로컬 처리기는 실측 후 선택적으로 추가한다.
- 미니PC는 개인·공유 웹 진입점, 메모·파일 저장, 검색, 작업 대기열, 공유 링크와 백업을 맡는다.
- OCR·할 일 추출·계획 정리·요약·조사는 사용자의 요청을 받은 작업자가 **설치된 에이전트를 실행**하거나 **외부 AI API를 호출**해 처리한다.
- 메모나 파일은 AI가 없어도 먼저 저장된다. 실행 경로가 설정되지 않았으면 AI 버튼에 준비가 필요하다고 표시한다.
- AI 결과는 원본을 덮지 않는 제안이며, 사용자가 검토·편집한 뒤 페이지나 할 일에 반영한다.
- 개인 기능은 Tailscale Serve가 식별한 본인에게만 열고, 공유 방문자는 로그인 없이 명시적으로 공유된 페이지만 읽는다. 에이전트 실행은 개인 진입점에서 본인이 요청한 작업에서만 시작한다.

### ‘에이전트’와 ‘API 호출’의 차이

| 실행 방식               | 동작                                                                              | 필요한 설정                                |
| ----------------------- | --------------------------------------------------------------------------------- | ------------------------------------------ |
| 설치형 에이전트 실행    | 미니PC의 격리된 실행기가 작업별로 에이전트 프로그램을 호출하고 결과를 앱에 돌려줌 | 에이전트 설치와 해당 제품의 인증·모델 연결 |
| 앱에서 외부 AI API 호출 | 사용자가 버튼을 누르면 서버 작업자가 설정된 AI API에 필요한 입력을 보냄           | 해당 제공자의 API 키                       |

에이전트는 **작업 흐름을 실행하는 프로그램**이다. 미니PC에서 그 프로그램을 실행해도 모델 자체를 미니PC에서 돌린다는 뜻은 아니다. 글·이미지 이해에는 에이전트가 연결한 원격 모델이 쓰일 수 있으며, 인증·비용은 선택한 에이전트 제품에 따른다. 앱은 특정 제품의 로그인 방식을 전제로 삼지 않는다.

## 2. 배포 구성

아래는 목표 운영 구성이다. 현재 앱은 개인 Node 서버 안에 비동기 작업자가 있고 별도 `server/public.mjs` 읽기 전용 공유 서버를 로컬/Compose에서 실행할 수 있다. Compose는 `storage`·`share` 두 서비스를 다른 네트워크와 루프백 포트로 띄운다. 별도 `worker`·Tailscale 본인 인증·실제 공개 도메인 연결은 아직 없다.

```text
본인 브라우저 ── Tailscale Serve (tailnet 전용) ──┐
공유 방문자 ── 공개 HTTPS / Cloudflare Tunnel ───┤
                                               ▼
┌──────────────────────────────────────────────────────────┐
│ N100 미니PC / Docker Compose                             │
│                                                          │
│ owner-web: 입력·검색·편집·관리·AI 요청 (호스트 루프백)    │
│ share-web: /s/* 읽기와 허용 파일만 (공개 Tunnel의 대상)   │
│   ├── /data/storage.sqlite                               │
│   └── /data/blobs                                         │
│ worker: URL 본문 추출·작업 큐·선택적 외부 AI API 호출      │
│ agent-runner: 설치된 에이전트 실행(선택적 격리 서비스)    │
│                                                          │
│ 선택적 로컬 OCR 처리기: 검증 후 작업자에 추가             │
│ 생성형 LLM 추론 서버는 기본 구성에 없음                  │
└──────────────────────────────────────────────────────────┘
```

`owner-web`, `share-web`, `worker`는 하나의 TypeScript 코드베이스에서 만든 동일한 앱 이미지의 별도 실행 명령이다. 공유 프로세스에는 업로드·개인 조회·AI·관리 라우트를 등록하지 않고 DB는 읽기 전용 연결로 연다. `agent-runner`는 선택한 에이전트 프로그램을 담은 별도 실행 환경이다. 원본 파일과 SQLite는 같은 호스트의 영속 볼륨에 둔다. SQLite WAL DB는 네트워크 드라이브에 두지 않는다. 운영에서 `owner-web`의 호스트 포트는 `127.0.0.1`에만 바인딩하고 Tailscale Serve가 연결한다. `share-web`은 공개 Tunnel의 내부 네트워크에만 붙이고 `owner-web` 컨테이너 네트워크에는 연결하지 않는다.

### 제안 스택

| 영역            | 첫 선택                                                            | 근거                                                             |
| --------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 웹 UI와 API     | React·TypeScript·Vite + Node 24; 개인/읽기 전용 공유 프로세스 분리 | 입력 화면 지연 로딩, 개인 쓰기/공개 읽기 권한 경계 분리          |
| 작업자          | 같은 코드베이스의 작은 Node 프로세스                               | URL 추출, 에이전트 실행 요청, 간헐적 API 호출을 웹 요청에서 분리 |
| 에이전트 실행기 | 선택한 CLI 에이전트를 담은 격리된 서비스                           | 웹 앱의 저장소·DB 권한 없이 작업별 입력만 처리                   |
| 메타데이터      | SQLite + 마이그레이션 도구                                         | 개인용 단일 호스트에 맞는 단순한 운영                            |
| 검색            | SQLite FTS5 v3의 위치 두 글자 토큰·고유 문자 열                    | 별도 검색 서비스 없이 원문·문서·파일명·할 일·AI 결과·OCR         |
| 업로드          | 로컬 SSD의 `/data/blobs`                                           | 별도 오브젝트 스토리지 없이 백업·이전 가능                       |
| 배포            | Docker Compose; 운영 시 Tailscale Serve와 선택적 `cloudflared`     | 로컬에서 개발한 구성을 미니PC에 옮기고 진입점만 환경별로 연결    |

현재 입력함은 React 19·Vite 6, API는 Node 24의 기본 HTTP·SQLite로 시작했다. 현재 AI 작업자는 같은 서버 프로세스 안에서 비동기로 실행한다. 공유 프로세스는 분리했으며 별도 AI/OCR worker 서비스 격리는 후속 구성이다. N100에서는 실제 파일 업로드·검색·백업 부하를 측정한다. 로컬 처리기를 선택하는 경우에만 해당 처리기의 품질·시간·메모리 사용량을 별도로 측정한다.

### 현재 통합검색

개인 로컬 `GET /api/search`와 모든 화면의 지연 검색 팔레트를 구현했다. 현재 정리 전 Capture 원문·URL과 불변 준비 요청, Page 제목·평문 본문/링크/표/자식/Mermaid, 활성 사용처가 있는 첨부 파일명을 검색한다. 정리 완료 메모·AI 요청은 제외하며 그 파일은 활성 참조 Page가 있을 때 검색하고 해당 Page로 이동한다. 원본·파일 바이트와 개인용 원본 접근은 유지한다. Task·완료 AI 결과·OCR 텍스트는 별도 확장 트리거로 FTS에 색인한다. 일반 파일 본문·URL 아카이브 본문은 후속 범위다. 공개 검색은 제공하지 않으며 미래 `share-web`에는 개인 검색 라우트를 등록하지 않는다. `/memo`의 LIKE·페이지 선택기의 제목 검색 API는 유지한다.

`server/search.mjs`·`searchText.mjs`가 같은 DB의 파생 평문·contentless FTS5·변경 번호와 순수 SQL 함수를 관리한다. 원본/참조 변경과 색인은 같은 트랜잭션이며 최초 backfill·v1→v2 원자 이관 후 정상 재시작에는 재색인하지 않는다. 원시 쓰기 연결도 트리거 함수 등록이 필요하다. 160 UTF-16/12단어·두 글자 이상 단어·혼합 한 글자·20개 커서·리셋 계약은 [현재 규격](CURRENT_IMPLEMENTATION.md#통합검색)을 따른다. 저장소 벤치마크는 임시 1만·10만 혼합 자료의 Apple M1 Max 실측이며 N100·HTTP 지연은 미측정이다. [측정·검증 기록](.omo/evidence/unified_search.md), [v2 보고서](.omo/evidence/search-benchmark-v2.json).

### 입력 화면의 성능 경계

입력 화면에는 작은 입력 폼·최근 항목만 싣고 블록 편집기와 AI 연결 코드는 페이지/설정 화면에서 별도로 불러온다. 목록은 페이지 단위로 읽고 업로드 이미지는 축소 미리보기를 사용한다. 원본 저장 요청은 SQLite·파일 기록이 끝나면 응답하며, OCR·요약·URL 본문 수집은 작업자에게 넘긴다. 장시간 작업이 입력 요청을 점유하지 않게 한다. 실제 성능 목표와 측정 자료의 크기는 [제품 계획](PLAN.md)의 응답성 항목을 따른다.

### 로컬 AI의 선택 기준

| 처리                                  | 기본 경로                      | 로컬 검토                                          |
| ------------------------------------- | ------------------------------ | -------------------------------------------------- |
| URL 본문 추출, 작업 종류 선택         | 일반 코드와 사용자가 누른 버튼 | 모델 불필요                                        |
| 스크린샷 글자 인식                    | 에이전트 또는 외부 API         | 한국어 OCR 처리기를 실제 스크린샷으로 비교 검증    |
| 할 일 추출, 계획 정리, 3줄 요약, 조사 | 설치형 에이전트 또는 외부 API  | 소형 생성형 모델은 품질·대기 시간 검증 후에만 검토 |
| 문서 자동 분류·중복 후보 판단         | 초기에는 없음                  | 사용량이 생기면 소형 판단 모델 검토                |

첫 버전에는 판단 모델을 배치하지 않는다. 작업 종류는 사용자가 선택한 버튼으로 결정한다. 향후 자동 분류가 필요해지면 실제 한국어 입력에서 일반 규칙보다 유용한지 검증한다.

## 3. 데이터 경계

아래 표의 본인 인증·영구 체크섬·OCR·작업별 파일 전달은 목표 설계다. 현재 원본·자산·문서·AI 작업·정리 상태·출처·AI 반영 직전 수정본·일반 수정 이력·페이지 템플릿의 실제 필드는 [현재 데이터 규격](CURRENT_IMPLEMENTATION.md#데이터-규격)을 따른다.

| 데이터                           | 저장 방식                                                                       | 접근                                                  |
| -------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `Capture`                        | 빠른 입력으로 저장한 메모·URL·유형·생성/수정 시각·버전. 사용자가 직접 수정 가능 | 본인; 작업 실행 시 필요한 범위만 에이전트 입력에 포함 |
| `Asset`                          | 파일 ID·체크섬·크기·MIME·불투명한 저장 키                                       | 본인; 작업별 임시 입력 또는 명시적 공유 링크          |
| `ProcessingJob`                  | 작업 종류·상태·입력 버전·실행 방식·재시도 정보                                  | 본인과 서버 작업자                                    |
| `DerivedContent`                 | OCR·요약·계획·할 일 제안과 출처                                                 | 본인; 공유 페이지에 넣은 내용만 방문자                |
| `Task` / `Page`                  | 사용자가 확정한 할 일과 버전이 있는 블록 페이지                                 | 본인; 공유 허용된 페이지만 방문자                     |
| `PageRevision` / `PageReference` | 복구 가능한 이전 문서와 페이지가 참조하는 파일·입력·페이지                      | 본인; 공유 렌더링 시 참조마다 권한 재검사             |
| `ShareGrant`                     | 토큰 해시·대상·만료·폐기·허용 파일                                              | 본인 설정; 유효 토큰 소지자는 읽기만                  |

원본 파일 경로는 URL에 노출하지 않는다. 현재 개인 파일 API는 활성 소유 Capture/Page, 활성 현재 본문·수정본 참조 또는 남아 있는 페이지 템플릿이 있을 때 연다. 개인 API 자체의 본인 인증은 아직 없으며 공유 파일 API는 토큰과 현재 본문의 직접 참조를 별도로 검사한다. 운영 단계에는 Tailscale 본인 식별과 작업 권한 검사를 추가한다. 검색 색인은 DB에서 재구축 가능한 파생 데이터다. 백업은 DB와 파일 집합을 함께 보존한다.

### 페이지 문서와 공유 렌더링

`Capture`와 `Page`는 별도 기록이다. 빠른 입력은 단순한 `Capture`로 저장하고 사용자가 정리할 때 선택한 내용·첨부·완료 결과를 기존/새/새 하위 `Page`에 담는다. 새 UI의 `disposition: 'organize'`는 메모 카드·태그를 본문에 넣지 않고 `page_origins`에 원본·선택 작업·정리 UUID를 기록하며 Capture의 `organized_at`·`organized_page_id`·`organized_operation_id`를 갱신한다. 문서·참조·출처·정리 상태·영수증은 한 트랜잭션이다. 복사한 블록을 편집해도 `Capture` 원문·버전·시각·첨부·AI 결과는 그대로 남는다. 정리 완료는 기본 메모/AI 목록·개수·검색에서 제외하고 명시적 `unorganize`로 복귀한다. 복귀는 현재 정리 작업 ID와 최초 영수증을 검사해 지연된 요청이 새 정리 상태를 해제하지 않게 한다.

`PageReference`는 본문 참조의 파생 색인이고 `page_origins`는 본문 밖의 출처다. 한 입력을 여러 페이지에서 재사용할 수 있으며 Page 정보는 새 출처·기존 가져오기 영수증·기존 원본 참조를 함께 조회한다. 기존 `captureRef`는 본문·Markdown에서 숨기되 저장된 JSON과 편집 후 숨긴 블록을 보존한다. `disposition`을 생략한 API는 이전 복사 계약을 유지하고 기존 UUID 재생은 원본의 정리 상태를 다시 바꾸지 않는다. 연결 Page의 휴지통 이동은 원본·파일을 삭제하거나 자동 복귀시키지 않는다.

`Page`는 제목, 스키마 버전, 편집 버전, 블록 문서 JSON을 보관한다. 블록마다 안정적인 ID를 두고 이미지·파일에는 디스크 경로나 공개 URL 대신 `Asset` ID를 연결한다. 저장 시 서버가 허용된 블록 구조를 검사하고 검색용 평문과 `PageReference`를 다시 만든다. Markdown은 가져오기·내보내기 형식이며 문서의 기준 데이터가 아니다. 자세한 편집 범위는 [페이지 편집 설계](PAGE_EDITOR_DESIGN.md)를 따른다.

선택한 완료 AI 작업의 **결과를 페이지로 정리**는 기존 `CapturePageImport`·페이지 가져오기 API를 재사용한다. 기본은 새 Page이며 기존 Page 끝이나 선택한 상위의 새 하위 Page도 지원한다. 클라이언트가 결과 Markdown·별도 출처 링크를 조립하고 제출 시 Markdown parser만 지연 로드해 블록으로 변환한다. 새 제목이 제안한 첫 H1과 같으면 본문 중복을 제거하며 기존 문서에 추가할 때는 H1을 유지한다. 서버의 선택적 `aiResult: {jobId, document}`는 해당 Capture의 `result_ready` 작업과 허용 문서·안전한 링크·1MB/1,000블록 상한을 검사하며 AI 본문 안의 개인 참조를 거절한다. 새 UI는 출처·정리 완료를 본문과 분리해 저장하며 원문 복사·첨부는 선택적으로 포함한다. 제출 UUID·작업 ID·변환 문서·대상·선택을 탭의 제출 사본에 보존하며 Page 쓰기·참조 색인·출처·정리 상태·영수증은 원자적이다. 응답 유실 뒤 pending 요청은 최초 UUID·문서로 확인하고 새 UUID의 명시적 가져오기는 새 블록 ID를 만든다. Page는 블록 JSON으로 편집·자동 저장하고 전체 Markdown 보기·복사를 제공한다. Capture·요청 사본·AI 작업 결과는 바뀌지 않는다. [구현 규격](CURRENT_IMPLEMENTATION.md#ai-결과-페이지-정리), [결과 변환 설계](docs/superpowers/specs/2026-09-29-ai-result-page-design.md)와 [수명 주기 설계](docs/superpowers/specs/2026-09-29-memo-page-lifecycle-design.md)를 따른다.

### 현재 Page AI와 결과 반영

`ai_jobs`는 nullable `capture_id`·`page_id` 중 정확히 하나를 소유자로 둔다. 이전 Capture 작업은 ID·UUID 지문·사본·결과·재시도 관계를 보존해 이관한다. Page 요청은 현재 `expectedVersion`을 검사하고 서버가 전체 저장 문서 또는 선택 루트/자식의 Markdown 입력을 64,000자 이내로 만든다. 제목·전체 문서·버전·선택 루트 ID·템플릿·추가 지시·조립 요청문을 불변 작업에 보관한다. 개인 참조·첨부·페이지 링크·목차 자체와 대상 본문·파일 바이트를 자동으로 전송하지 않는다. 미저장·충돌·복구 상태에서는 제출을 막고 작업 실행 중에는 문서를 계속 편집한다.

완료된 해당 Page 작업은 `append`·`replace`·`child`로 명시 반영한다. 새 블록을 검증·재식별하고 비선택 블록·첨부·목차·페이지 링크는 유지한다. `replace`는 선택 기록과 요청 당시 문서 버전이 유지돼야 한다. 모든 반영은 현재 `expectedVersion`을 검사하며 `append`·`replace`의 직전 제목·문서·반영 버전을 `page_ai_revisions`에 남기고 `page_ai_applies` 영수증과 원자적으로 저장한다. `page_ai_undos`는 반영 이후 버전이 그대로일 때만 직전 문서를 새 버전으로 복원한다. 새 하위 Page는 기존 휴지통으로 되돌린다. 일반 수정 이력은 별도 `page_revisions`에 최근 100개를 저장하고 버전 검사 후 새 버전으로 복원한다. 전체 문서를 Markdown으로 왕복 교체하지 않는다.

지연 Page AI 도구는 템플릿·상태·이력·Markdown 변환을 재사용한다. 페이지별 `localStorage`는 요청·반영·되돌리기 UUID·최초 본문·경로와 마지막 반영 기준을 보존한다. 응답 유실·이동·새로고침 뒤 같은 제출 사본으로 확인하고 영수증을 버전 검사보다 먼저 조회한다. pending은 새 AI 제출을 막고 문서 반영/되돌리기 또는 손상된 복구는 편집도 잠근다. 추가·교체·되돌리기 성공 뒤 최신 Page를 다시 조회해 오래된 영수증 반환값이 새 편집을 덮지 않게 한다. [현재 Page AI 규격](CURRENT_IMPLEMENTATION.md#페이지-ai)을 따른다.

현재 공유 화면은 편집기를 노출하지 않고 `server/publicPage.mjs`가 이스케이프한 읽기 전용 HTML을 만든다. `page_shares`의 32바이트 토큰 해시·만료·폐기·현재 페이지 활성 여부를 매 요청에 검사한다. 첨부는 현재 문서의 `asset`·`map`·`itinerary` 블록이 직접 참조하는 ID만 공유 주소로 연다. 내부 페이지 링크는 제목도 공개하지 않고 원본 메모 블록은 숨긴다. 개인 출처·AI 작업/반영 API는 공유 프로세스에 등록하지 않으며 저장된 Page 문서에 토큰을 기록하지 않는다. Mermaid는 공개 HTML에서 코드 텍스트로 표시한다. 파일의 명시적 개별 공유·하위 페이지 묶음 공유는 아직 없다.

### 일정·페이지 도구·수정 이력

`shared/itinerary.ts`는 한국시간 일정 최대 50개와 선택적 활동 유형을 검증하고 소요시간·겹침·방문 번호를 계산한다. `shared/itineraryPreview.ts`는 외부 지도 데이터 없이 좌표 기반 방문 위치·순서 SVG를 만든다. 개인 다중 장소 지도만 Google SDK를 지연 로딩한다. 공유는 정적 이미지·외부 Google 링크이며 지도 SDK·OSM·Leaflet을 요청하지 않는다. `map`/`itinerary`의 선택적 `assetId`는 기존 이미지 첨부를 재사용하고 현재 공유 범위·개인 수정본·템플릿의 파일 보존 참조에 포함된다. 기존 일정 JSON version 1과 단일 장소·표·파일 바이트는 유지한다.

`server/pageTools.mjs`는 단일 페이지 복제(하위 트리 제외), 저장 문서의 사용자 템플릿, Page 직접 첨부, 두 페이지 버전을 확인하는 원자적 블록 이동, 일반 수정 이력을 맡는다. 복제·템플릿 생성/저장·첨부·이동·수정본 복원은 UUID의 최초 요청/응답을 보관해 응답 유실 재시도에서 중복을 막는다. 첨부 바이트는 복제·이동하지 않고 기존 ID를 재사용하며 직접 업로드만 새 Page 소유 자산을 만든다. `assets` 이관은 기존 ID·rowid·저장 키·Capture 소유권을 보존하고 nullable `capture_id`/`page_id` 중 하나의 소유자만 허용한다.

`page_revisions` 트리거는 생성과 모든 버전 변경(편집·AI 반영·메모 담기·서버 변경)을 기록하고 페이지별 최신 100개를 유지한다. 기존 DB에는 이관 당시 현재 버전만 최초 기록한다. 복원은 제목·아이콘·본문을 현재 계층/위치 그대로 새 버전으로 저장한다. 수정본·페이지 템플릿은 개인 첨부 보존 참조를 가지며 공개 링크는 현재 본문만 읽는다. 파일명 검색도 활성 현재 소유자/본문 범위에 한정한다. [현재 규격](CURRENT_IMPLEMENTATION.md#페이지-도구와-수정-이력)과 [보존 설계](docs/superpowers/specs/2026-09-30-plan-page-preservation.md)를 따른다.

## 4. 처리 작업 계약

2026-09-29 현재 프롬프트 관리·불변 수정본·Capture의 요청 사본과 **AI 작업 큐·실행·결과·이력**, URL·키워드 리서치를 구현했다. [AI 실행 설계](docs/superpowers/specs/2026-09-29-ai-execution-design.md), [키워드 확장 설계](docs/superpowers/specs/2026-09-29-keyword-research-design.md)와 [현재 규격](CURRENT_IMPLEMENTATION.md#ai-요청-실행)이 실행 기준이다. 기본 템플릿 4개 중 `research-keyword`는 기존 DB에 해당 ID가 없고 템플릿이 200개 미만일 때만 추가하며 기존 수정·보관·수정본을 보존한다. 2026-09-28 [하네스 초안](docs/superpowers/specs/2026-09-28-ai-request-harness-design.md)은 당시 구상과 후속 범위를 보존한다. 독립 `Task`는 AI 없이도 직접 관리한다.

### 현재 저장·작업자

AI 체크 후 저장은 원본·첨부 메타데이터·불변 요청 사본·UUID 제출 기록·대기 작업을 같은 SQLite 트랜잭션에 남긴다. HTTP 저장 응답은 처리 완료를 기다리지 않는다. `capture_submissions`는 재제출 지문을, `ai_jobs`는 원본 버전·요청 스냅샷·실행 상태/토큰·결과·오류·시각·재시도 연결을 보관한다. 결과는 원본 내용·첨부·생성/수정 시각을 바꾸지 않는다.

현재는 서버 프로세스 하나·DB 하나·비동기 작업자 하나다. `queued → running → result_ready | failed`, 작업 120초·응답 256KiB 계약이며 상태/토큰이 일치할 때만 완료한다. 재시작 시 queued는 보존하고 미완료 running은 interrupted 실패로 남긴다. 자동 유료 재시도·제공자 전환·이전 prepared/예시 자동 실행은 없다. **현재 메모로 다시 요청**은 현재 저장 원문과 처음 보관한 템플릿·추가 지시를, **실패한 요청 그대로 재시도**는 이전 작업 사본을 사용한다. **요청 당시 입력·프롬프트**는 선택한 작업의 사본을 보여준다. 현재 버전과 다르면 이전 내용 기준을 표시한다. 휴지통 원본의 이력은 숨기고 실행 전 이동된 작업은 전송하지 않는다.

### 설치형 Devin 실행기

`AI_RUNNER_KIND=devin`은 서버 환경에 설치·인증된 Devin CLI를 명시적으로 선택한다. `AI_DEVIN_BIN`(기본 devin)·`AI_DEVIN_MODEL`(기본 swe-2-high)을 설정할 수 있다. Devin CLI는 실행기이며 앱은 모델 설정값을 `--model`로 명시적으로 전달하고 완료 결과에 작업의 실행기·모델을 구분해 표시한다. 2026-09-29 사용자 요청으로 기본 모델을 SWE-2 High로 변경했으며 이전 작업의 모델 이력은 보존한다. 원문·URL 문자열과 수집 자료만 작업별 임시 공간의 0600 입력/설정 파일로 준비한다. 첨부 바이트·DB·전체 업로드 디렉터리를 전달하지 않는다. 고정 `spawn` 인자·최소 환경을 사용하고 앱/API 키를 자식 환경에 넣지 않는다. 키워드 검색 단계는 `web_search`만 허용하고 요약은 웹 검색도 금지한다. 두 단계 모두 파일·셸·Fetch·MCP·하위 에이전트와 다른 에이전트 설정 가져오기·자동 업데이트를 끈다. 검색·요약 CLI 2회는 수집까지 같은 작업의 120초 deadline·동시 작업 1개·중단 signal을 공유한다.

이 구성은 **OS 샌드박스가 아니며** 설치된 CLI의 인증 저장소·외부 제공자는 유지된다. Mac/Linux에서는 소유 POSIX 프로세스 그룹에 SIGTERM을 보내고 200ms 뒤 SIGKILL로 강제 종료한다. 실제 child close·임시 공간 정리·`runner.drain(signal)`을 기다린 뒤 실패 기록·다음 작업·서버 종료를 진행한다. Windows의 직접 자식과 소유 그룹을 벗어난 프로세스는 같은 보장 범위가 아니다. 앱은 CLI를 자동 설치/로그인하지 않으며 Docker 기본 이미지에도 CLI·인증이 없다. 운영 대상의 설치·인증은 별도로 준비한다.

### HTTP 게이트웨이 실행기

`AI_RUNNER_KIND=http`와 `AI_RUNNER_URL`, 선택적 서버 비밀 `AI_RUNNER_TOKEN`을 사용한다. KIND 없이 URL만 설정하는 계약도 지원한다. HTTPS 또는 루프백 HTTP만 받고 credentials/redirect를 거절한다. 요청은 schemaVersion·jobId·kind·prompt·input·materials·policy를 담는 앱 전용 JSON이다. 제공자의 직접 OpenAI/Anthropic API 형식이 아니며 게이트웨이가 번역한다. policy는 도구 사용 금지·4096 출력 토큰·자료를 데이터로 취급하는 조건을 전달한다. HTTP에는 검색 capability가 없고 키워드 작업은 `research_search_unavailable`로 요약 호출 전에 실패한다. 제공자별 검색 API는 추가하지 않았다.

응답 `{markdown, sources?, usage?}`를 공통 검증한 뒤 작업에 저장한다. 리서치 출처는 서버 수집 URL과 대조하고 자유 요청 링크는 본문 미확인으로 표시한다. 사용량 미보고는 null이며 현재 비용 집계는 없다. HTTP 호출은 deadline/abort로 제한하지만 이미 진행 중인 제공자 작업·과금 취소를 보장하지 않는다. 키·프롬프트·원문·공급자 오류 본문은 로그/클라이언트 오류에 노출하지 않는다.

실행기는 기본 비활성이다. 미연결은 원본 저장 성공 뒤 runner_unavailable 실패로 표시한다. 상태 API의 `researchModes`는 비활성 `[]`·Hive/HTTP `['url']`·OpenCode/Devin `['url', 'keyword']`다. 실제 adapter의 discover 함수에서 지원 여부를 계산한다. 일반 테스트는 임시 HTTP 응답·가짜 CLI를, 설정된 결과 UI QA와 `scripts/qa-keyword-research.mjs`는 임시 DB·로컬 HTTP fixture를 사용한다. `scripts/ai-devin-smoke.mjs`만 명시적인 합성 입력 실호출이며 일반 검증에 포함되지 않는다. `DEVIN_SMOKE_RESEARCH=1`의 공개 주제 smoke는 실행당 앱 작업 하나·CLI 2회와 외부 계정 사용량·요금을 발생시킬 수 있다. 이전 키워드 증거에는 최초 검색 probe·키워드 작업 2개가 포함된다. 현재 Page AI 작업의 실호출 검증 기록은 아니다. 기록된 실호출은 result_ready·원본 보존·usage null이며 제공자의 정확한 비용/내부 호출 수는 확인하지 않았다. [검증 기록](.omo/evidence/keyword_research.md)을 따른다.

### 후속 처리·격리 목표

OCR 단일 큐·외부 HTTP 게이트웨이 계약, 선택한 AI 결과의 Task 채택, 완료 결과 검색을 구현했다. OCR은 별도 저장/작업자이며 실제 제공자 연결·첨부 일반 이해·별도 worker/agent-runner 서비스와 OS 격리는 후속 설계다. 장비별 실행·인증·메모리·비용 정책은 배포 전 검증한다. N100 상주 생성형 LLM은 기본 전제로 두지 않는다.

## 5. URL과 조사 흐름

현재 `kind: research`는 URL이 있으면 공개 HTTP·HTTPS URL 하나의 HTML/평문을 수집하고 URL 없는 비어 있지 않은 주제는 OpenCode·Devin의 선택적 `discover`로 검색한다. URL/DNS와 리다이렉트마다 비공개·예약 주소를 거절하고 검사한 IP로 연결을 고정한다. 한 URL의 한도는 10초·리다이렉트 3회·2MiB·추출 텍스트 50,000자다. 키워드는 검색 1회·240자 이하 질의·최대 5개 후보를 지시하며 1MiB 이하 ATIF의 실제 `web_search` 1개·연결된 관측 URL과 최종 후보를 검사한다. 256KiB 출력·검색 export 검사는 호출 후 검증이며 과금 상한·OS 샌드박스가 아니다. 고유 후보 최대 5개를 순차 수집해 고유 최종 URL 본문 최대 3개·각 16,666자/합계 49,998자를 사용한다. 실패 후보는 건너뛰고 본문이 없으면 요약 전에 `research_no_sources`로 실패하며 부분 수집은 결과에 안내한다. 원본을 보존하고 주제·URL 수정이나 재시도는 명시적으로 요청한다. 자유 요청은 검색하지 않는다. 아래 무제한 웹 탐색·자동 제목 추출 등은 후속 목표다.

- URL 입력은 AI 사용과 관계없이 주소와 제목/기본 메타데이터를 보존한다.
- 서버 작업자가 공개 HTTP/HTTPS URL의 본문을 가져올 수 있다. 내부망·로컬 주소와 리다이렉트 우회를 막고, 응답 시간·크기를 제한한다.
- 본문 추출 뒤 설치형 에이전트나 외부 API가 3줄 요약을 만든다. 외부 사이트가 수집을 막으면 원래 URL과 실패 이유가 남는다.
- 조사 주제는 검색 결과나 사용자가 제공한 URL 같은 **출처 자료**가 있어야 한다. 에이전트가 웹 탐색 기능을 갖고 있으면 그 결과를 제출할 수 있고, 그렇지 않으면 앱에 추가한 URL 묶음을 자료로 처리한다.
- URL 본문과 검색 결과는 신뢰할 수 없는 자료로 취급한다. 그 안의 지시문이 앱 권한, 작업 범위 또는 공유 설정을 바꾸지 못하게 한다.

## 6. 본인 인증과 공유

아래의 본인 인증은 후속 구현 목표다. 현재 개인 API는 루프백에만 바인딩하며 본인 인증이 없다. 로컬 공유 서버는 별도 프로세스·읽기 전용 DB 연결·토큰 검사로 제한한다. 개인 API를 공개 인터넷에 연결하지 않는다.

- 운영의 개인 서비스는 Tailscale Serve만 진입점으로 사용한다. Serve의 `Tailscale-User-Login` 헤더가 설정한 본인 식별자와 정확히 일치할 때만 개인 화면/API를 처리한다. 헤더가 없거나 다른 사용자면 거부하며, 공개 가입·앱 비밀번호·비밀번호 재설정 화면은 첫 버전에 두지 않는다.
- 개인 서비스의 호스트 포트는 루프백에만 열어 Serve가 보낸 식별자 헤더를 다른 네트워크 경로에서 위조하지 못하게 한다. 개인용 쓰기 API에는 Origin/CSRF 검사를 적용한다. tailnet에 다른 사용자를 추가하면 접근 정책도 본인 기기로 제한한다.
- 개발용 인증 우회는 개발 모드와 로컬호스트 바인딩이 모두 충족될 때만 허용하고 운영 모드에서는 시작 자체를 거부한다. Tailscale 계정이나 기기에 문제가 생겼을 때는 미니PC의 로컬 콘솔/관리자 접속으로 Tailscale 설정을 복구한다. DB·파일 복구는 별도 백업 절차를 따른다.
- 공유 방문자는 `/s/{token}`의 읽기 전용 본문을 보고, 허용된 링크에서만 `/s/{token}/comments`로 이름 댓글/답글을 남긴다. 공유는 기본 비공개·댓글 꺼짐이며 만료·폐기 가능이다.
- `share-web`은 공유 페이지·허용된 파일·필요한 정적 리소스만 제공한다. 개인 API 라우트가 없고 Tailscale 식별자 헤더를 인증에 사용하지 않는다.
- 페이지 본문 수정은 기존 공유 링크에 반영된다. 새 첨부 **블록**을 공유 페이지에 넣으면 그 파일도 공유 범위에 들어간다. 발급 화면은 현재 첨부 목록을 보여주고 발급한 링크를 공개 뷰에서 열어 방문자 권한으로 확인할 수 있다.
- 공유 페이지와 파일은 `Cache-Control: no-store`, `Referrer-Policy: no-referrer`로 제공한다. 각 파일 요청에서 공유 권한을 다시 검사한다.
- 에이전트 실행기는 Tailscale 식별자 헤더나 서버 관리 토큰을 받지 않는다. 페이지 공유·사용자 설정·다른 작업의 원본 접근 권한을 주지 않는다.

## 7. 도메인과 외부 접속

아래 주소·Tunnel·Serve 연결은 후속 운영 계획이다. 현재 로컬/Compose 공유 경로는 `127.0.0.1:8790/s/{token}`으로 제공한다.

| 방식                                        | 사용 시점                       | 제약                                                                    |
| ------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------- |
| Tailscale Serve의 `*.ts.net`                | 개인 화면의 기본 주소           | 본인 tailnet에 가입한 기기에서만 접근                                   |
| Tailscale Funnel의 `*.ts.net`               | 도메인을 사기 전 공유 시범 운영 | 공개용이며 베타·대역폭 제한이 있음; Serve와 같은 포트를 함께 쓸 수 없음 |
| 본인 도메인의 `share.*` + Cloudflare Tunnel | 오래 사용할 공유 링크 운영      | 도메인을 등록하고 Tunnel을 공유 서비스에만 연결                         |
| Cloudflare Quick Tunnel의 임시 주소         | 공유 화면 개발·테스트           | 지속 운영을 위한 주소가 아님                                            |

예를 들어 개인용은 `mini.<tailnet>.ts.net`, 공유용은 `share.example.com`으로 분리한다. 두 주소가 같은 기본 도메인 아래에 있을 필요는 없다. 주소 이름보다 중요한 것은 개인 주소가 공개 Tunnel에 연결되지 않는다는 점이다. 현재 앱은 `PUBLIC_SHARE_ORIGIN`으로 공유 링크 기본 주소를 정한다. 공유 주소를 바꾸면 기존 수신자에게 새 주소를 다시 보내거나 이전 주소를 유지한다.

개인 업로드는 Cloudflare를 통과하지 않으므로 Cloudflare 무료 요금제의 요청당 100MB 업로드 제한이 적용되지 않는다. 단일 파일 90MB는 초기 구상이었고, 현재 구현 상한은 25MB다. 실제 사용량을 보고 배포 전 상한을 다시 결정한다. 공유 공개 서비스는 업로드 요청을 받지 않는다.

### 로컬 개발에서 미니PC로 이동

현재 수동 `npm run backup -- create|verify|restore` 도구는 운영 중인 SQLite의 일관된 사본과 그 DB가 참조하는 첨부를 검사해 새 경로에 복원한다. 기존 자료는 덮어쓰지 않는다. 개인 `/backups` 화면의 일일 예약·수동 실행·상태도 구현했다. 처음에는 꺼짐, 기본 04:00 한국시간·7개 보관이며 1~60개로 설정한다. 검증된 새 사본을 만든 뒤 관리 중인 정상 백업만 정리하며 미완료 실행·재시작 중복을 처리한다. 복원은 CLI의 존재하지 않는 새 데이터 경로만 허용한다. 별도 디스크/원격 보관과 N100 운영 검증은 후속 단계다.

현재 Compose는 같은 이미지의 `storage`와 `share` 서비스를 별도 네트워크·루프백 포트로 실행한다. `storage`는 SQLite·첨부를 `./data:/data`로 읽고 쓰고 자동 백업은 `BACKUP_DIR=/backups`와 별도 `./backups:/backups` 볼륨을 사용한다. `share`는 데이터만 읽기 전용으로 마운트하며 백업 볼륨/API는 없다. Docker 개인/공개 분리·재시작 후 유지·읽기 전용 범위를 로컬 QA로 확인하고 Linux/amd64 이미지도 빌드/실행 검증한다. 실제 N100 성능과 외부 네트워크는 운영 장비에서 확인한다.

현재 Compose에서 개인 웹은 `127.0.0.1:8787`, 공유 웹은 `127.0.0.1:8790`으로 분리했다. 운영 주소, Tailscale, Cloudflare는 로컬 공유 시험의 필수 조건이 아니다. Docker 이미지 안에 DB·파일·비밀값을 넣지 않고 환경 설정과 영속 볼륨으로 분리한다.

N100은 `linux/amd64` 대상이므로 로컬 개발 컴퓨터가 다른 CPU 아키텍처라면 대상용 이미지를 별도로 빌드하거나 다중 플랫폼 이미지로 배포한다. 이전 순서는 `일관된 DB/파일 백업 → 미니PC 복원 → Compose 기동 → 개인/공유 경로 검증 → Tailscale Serve와 공개 Tunnel 연결`이다. 복원 전의 로컬 DB를 실행 중인 상태에서 단순 복사하지 않는다.

자동 백업의 기본 경로는 `dirname(realpath(DATA_DIR)) / (basename(DATA_DIR) + '-backups')`이며 데이터와 백업 경로가 같거나 서로 조상/자손 관계이면 거절한다. 기본 경로는 실제 데이터 디렉터리와 형제인 별도 트리다. 예약 설정·실행 이력은 백업 폴더의 `automatic-backups.json`에 있으므로 DB 스냅샷과 별도로 이전한다.

이전 가능한 서버 데이터와 브라우저 초안을 구분한다. Capture·Page·Task·프롬프트·불변 수정본·가져오기 매핑·정리 상태/복귀 영수증·출처·AI 작업/결과/제출·반영 직전 수정본/반영/되돌리기 영수증·일반 페이지 수정본·페이지 템플릿·페이지 도구 영수증·첨부는 서버 저장소를 복원한다. 현재 템플릿의 JSON 교환도 구현했으며 이력은 포함하지 않는다. 이전 브라우저 템플릿은 서버로 가져온 뒤 백업한다. 최근 선택·미저장 초안·Page AI 미확인 제출/마지막 반영 기준은 origin(프로토콜·호스트·포트)에 속하므로 서버 디렉터리 복사로 이전되지 않는다. 미확인 요청은 같은 주소에서 확인하고 임시 초안은 먼저 명시 저장하거나 복사해 둔다. [브라우저 저장 범위](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [SQLite 일관된 백업](https://www.sqlite.org/backup.html)

기본 이미지는 서버와 작업자만 포함한다. 현재 Devin 경로를 배포하려면 대상 환경에 CLI·인증·실행기 설정을 준비하거나 HTTP 게이트웨이를 연결한다. 별도 실행기 이미지·OS 격리는 후속 구성이다. Mac에만 설치된 실행 파일을 옮기는 방식은 사용하지 않는다. 주소·환경 변수·인증/공유 진입점·백업 복원과 대상 성능은 운영 환경에서 확인한다.

## 8. 운영과 개발 순서

1. **로컬 기반:** Compose에서 개인/공유 웹·SQLite·파일 저장·백업을 실행한다. 공유 웹에 개인 경로가 없는지와 저장 응답 측정 방법을 확인한다.
2. **빠른 입력:** 모바일 입력함, URL·스크린샷·파일 보존, 최근 목록·한국어 검색을 만든다. 입력 화면에 편집기 코드를 싣지 않고 실제 휴대폰에서 속도를 측정한다.
3. **블록 페이지:** 편집기 후보를 작은 실제 페이지로 검증한 뒤 기본 블록, 자동 저장·복구, Capture 연결과 첨부를 붙인다. 페이지 진입 시 편집기 코드를 불러온다.
4. **AI 처리:** 작업 대기열·공통 결과 계약을 검증하고 선택한 에이전트 프로그램을 실행기에 설치한다. 사용자가 원하면 직접 외부 AI API 호출 설정을 추가한다. OCR 게이트웨이 연결 후 실제 한국어 스크린샷 품질을 검증한다.
5. **공유:** 공개 모드의 읽기 전용 페이지·파일, 첨부 허용 범위, 미리보기, 링크 만료·폐기를 로컬에서 완성한다.
6. **미니PC 이전·운영:** N100에서 백업을 복원하고 Tailscale Serve 본인 식별과 공개 Tunnel의 공유 경계를 확인한다. 출처 있는 조사, 백업 복원 연습, 작업 상태·외부 API 사용량을 붙인다.

미니PC 사양은 앱 호스팅 계획에 반영했다. 현재 Mac의 설치·인증된 Devin CLI는 합성 입력으로 확인했으며 대상 Linux/amd64의 비대화형 실행·인증·성능은 별도 확인한다. 앱의 저장·작업·공유 데이터 계약은 그 선택과 분리한다.

### 배포 전 확장 계약

개인 블록 댓글은 문서와 독립된 스레드 버전으로 저장한다. 오프라인 ZIP은 현재 직접 참조 파일만 스트리밍하고, Task 채택은 선택 항목과 UUID 영수증을 원자적으로 저장한다. OCR 큐는 동시에 한 이미지만 처리하며 원본을 바꾸지 않는다. 확장 검색은 같은 SQLite 쓰기의 트리거로 유지하고 재구축할 수 있다. 프롬프트 과거 수정본은 초안으로 불러와 새 버전으로 저장한다. 실제 API/한도는 [현재 구현](CURRENT_IMPLEMENTATION.md#2026-09-30-배포-전-완성-항목)을 따른다.

### 이름 기반 공유 댓글 실행 경계

현재 공개 댓글은 별도 `shared_comment_*` 테이블과 UUID/대화 버전을 사용한다. 개인 댓글은 공개하지 않고 원본 문서 버전을 바꾸지 않는다. 같은 페이지의 활성 댓글 허용 링크에서 공유 대화를 이어간다. 방문자는 로그인 없이 이름 1~30자·댓글/답글만 남기며 본인 확인 기능은 없다. 개인 화면만 작성자 답글·해결·삭제를 관리한다.

공개 프로세스는 기존 `:ro` 데이터/SQLite 연결을 유지한다. 개인 프로세스가 `COMMENT_SOCKET_PATH` Unix socket으로 댓글 전용 broker를 열고 공개 서버는 정해진 GET/POST 경로만 전달한다. broker가 토큰/허용/현재 공개 블록/한도/버전을 다시 검사하며 개인 API는 제공하지 않는다. 같은 SQLite이므로 기존 온라인 백업은 공유 댓글과 영수증도 보존한다. Compose의 `comment-ipc`만 두 컨테이너에 연결한다. 새 댓글 경계의 테스트와 기존 Docker 검증 기록은 구분한다.

운영 주소 예시는 개인 `mini.<tailnet>.ts.net` 또는 Tailscale로 제한한 `app.example.com`, 공개 `share.example.com`이다. `PUBLIC_SHARE_ORIGIN`을 두 프로세스에 동일하게 설정한다. 주소 이름은 권한이 아니므로 개인 서버를 공개 Tunnel에 연결하지 않는다. 실제 DNS/Tunnel 연결은 이번 로컬 구현에 포함하지 않는다.

## 이전 전 연결 계층 (2026-09-30)

SQLite에 공유 댓글 받은함의 파생 활동/guest sequence/읽음 marker와 일정 private 관계를 추가한다. 같은 온라인 DB 스냅샷에 포함하고 재시작 후 migration을 안전하게 재실행한다. 받은함 최근 목록은 인덱스/cursor와 제한된 메타데이터를 사용한다. 일정 public projection은 허용된 현재 블록/항목과 opt-in Task 제목/상태만 반환한다. 공개 프로세스의 readonly DB와 제한된 comment socket 경계는 유지한다. 모바일 공유 대기함은 private origin IndexedDB이며 서버 백업 대상이 아니고 명시 저장 이후 서버 데이터가 된다. manifest/service worker는 personal app에만 배포하며 전체 오프라인 동기화는 없다. Docker 경로 설정·백업 CLI·확인 명령·실제 이전 절차는 [DEPLOYMENT](docs/DEPLOYMENT.md)를 따른다.

### 구현 추가: 일지·독립 정적 사이트 (2026-10-05)

일지의 서버 진입은 기존 `/api/sync`이며 `server/journal.mjs`와 `shared/journal.mjs`가 날짜별 엔티티/검증을 맡는다. 브라우저 `src/journal/storage.ts`가 controller에 기존 IndexedDB 저장·큐·변경 구독을 연결한다. 전체 날짜 충돌을 보존하며 localStorage 자료는 원문 사본을 남기는 이관 입력이다. `src/journal/migration.ts`는 기기 공통 원문 소유권과 원문 보관·원자 이관을 맡고, `LegacyJournalReview.tsx`는 두 기기 사본이 겹칠 때의 선택을 제공한다. 현재 입력 화면과 서버 캐시가 달라지면 입력 화면이 보던 base를 사용해 조용한 덮어쓰기를 막는다.

정적 호스팅은 별도 `server/sites.mjs`8792와 HOSTED_SITES_DIR registry/bundles 파일 저장으로 구현했다. 개인 서버의 `server/hosting/routes.mjs`만 등록/공개 상태를 쓰고 정적 프로세스는 읽기만 한다. `src/hosting/HostingWorkspace.tsx`가 `/hosting` 관리 목록이고 설정에서 진입한다. Compose sites는 사이트 볼륨만 읽기 전용 마운트하며 Caddy가 host.leneu.store를8792로 프록시한다. 실제 원격 배포는 후속이다. 상세 파일/제한/운영 방법은 [STATIC_HOSTING.md](docs/STATIC_HOSTING.md).
