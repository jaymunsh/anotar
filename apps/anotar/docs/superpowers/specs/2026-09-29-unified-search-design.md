# 통합검색 설계

## 목적과 실행 범위

주로 한 사람이 사용하는 leneu.에서 메모·준비된 AI 요청·페이지 제목과 본문·첨부 파일명을 같은 검색창으로 찾는다. N100(16GB RAM, 로컬 SSD)에 이전할 수 있도록 기존 Node 24·SQLite 안에 검색을 넣는다. 이 문서는 검색 구조와 자원 소비를 논의한 뒤 사용자가 요청한 개발 재개의 범위다. 현재 공유 작업 트리에서 직접 구현하며 이전 작업과 실제 `data/`를 보존한다. 커밋·외부 배포는 이 작업에 포함하지 않는다.

## 선택한 구조

- SQLite FTS5 하나를 사용한다. 별도 검색 서비스·새 패키지·LLM은 필요하지 않다.
- `search_documents`는 검색용 평문과 작은 결과 메타데이터를 저장하는 파생 테이블이다. 페이지 블록 JSON은 저장 시 한 번 평문으로 변환한다.
- `search_fts`는 `content=''`, `contentless_delete=1`로 평문·인코딩된 색인 입력을 재복제하지 않는다. 위치 정보는 유지하여 두 글자 토큰의 연속 구문 검색을 정확하게 수행한다.
- 스키마 v2는 같은 FTS에 중복을 제거한 한 글자 토큰 열을 추가한다. 혼합 질의의 짧은 조건도 색인에서 확인하며 후보 본문을 다시 정규화하지 않는다. 기존 v1 색인은 한 트랜잭션에서 재구축하고 원본 기록은 수정하지 않는다.
- SQLite의 순수 함수와 트리거로 Capture·Page·Asset·page_references 변경을 같은 쓰기 트랜잭션 안에서 반영한다. 실패·409·가져오기 롤백은 검색에도 남지 않는다.
- `search_state`의 변경 번호로 검색 결과 페이지 사이의 변경을 감지한다. `search_meta`의 스키마 버전은 최초 이관/명시적인 파생 색인 재구축을 구분한다. 정상 재시작 때 전체 데이터를 다시 색인하지 않는다.

## 검색 의미

- 입력은 최대 160 UTF-16 코드 단위, 공백으로 분리한 단어는 최대 12개다. NFC 정규화·소문자화·연속 공백 정리를 적용한다. `%`, `_`, 따옴표, `AND`, 이모지는 일반 글자다.
- 공백으로 나눈 단어를 모두 포함하는 기록을 찾는다. 한 단어의 글자는 한 필드 안에서 연속해야 한다. 두 글자 토큰을 코드 포인트 기반 ASCII 문자열로 인코딩하여 FTS5 `unicode61`에 전달하며, 질의도 서버에서 만든 인코딩 구문만 사용한다.
- `여행`은 `주말여행준비`를 찾는다. 띄어쓰기 없는 두 글자 부분 검색도 지원한다. 원문의 토큰 순서를 유지하여 서로 떨어진 `ab`와 `bc`를 `abc`로 잘못 찾지 않는다.
- 두 코드 포인트 이상인 단어 하나가 있어야 본문 검색을 시작한다. 한 글자만 입력하면 `reason: short_query`를 반환한다. `교토 3`처럼 긴 단어가 있는 질의의 한 글자 단어는 같은 FTS의 문자 열에서 확인한다. 검색창은 짧은 입력에 `두 글자 이상 입력해 주세요.`를 표시한다.
- 빈 입력에서는 최근 활성 기록 20개를 제공한다. 휴지통 기록은 결과에서 제외한다.
- 제목/파일명·URL에 본문보다 높은 FTS5 BM25 가중치(10·3·1)를 부여하고, 동점은 내부 행 ID 내림차순으로 정한다. 제목 있는 Page와 파일명만 제목 필드에 색인한다. 메모에 새 제목을 만들지 않는다.

## 색인 내용과 경계

| 분류 | 색인 내용 | 결과 이동 |
| --- | --- | --- |
| `memo` | 현재 Capture 원문·URL | `/captures/:id` |
| `ai` | 현재 원문·URL 및 저장 당시 입력·템플릿 이름·조립 요청문 | `/captures/:id` |
| `page` | 제목, 문단·리스트·코드·Mermaid·표·자식 블록의 작성 텍스트와 링크 주소 | `/pages/:id` |
| `file` | 파일명 | 활성 소유 Capture, 없으면 해당 파일을 참조하는 활성 Page |

- 페이지의 DB ID·스타일·참조 ID·다른 문서의 원문은 본문 색인에 섞지 않는다. 실제 복사한 본문은 해당 페이지에 색인한다.
- 파일 본문·OCR·PDF 내용·외부 URL 본문은 이 기능의 검색 대상이 아니다. 파일명만 검색한다.
- AI 요청은 별도 분류와 필터로 노출하며 실행 결과로 표시하지 않는다.
- 첨부는 활성 소유 Capture 또는 활성 참조 Page가 있을 때만 검색한다. 참조가 제거되거나 모두 휴지통으로 이동하면 파일 결과도 사라지고 복원하면 다시 나타난다.
- 검색은 현재 개인 로컬 API에만 추가한다. 이후 공유 서버는 이 개인 검색 API를 등록하지 않는다.

## API

`GET /api/search?q=&type=all|memo|ai|page|file&cursor=`

- 응답: `{ items, nextCursor, reset, reason }`. 최대 20개, 결과마다 `id`, `type`, `label`, `snippet`, `icon`, `kind`, `createdAt`, `updatedAt`, `href`, `context`를 제공한다. `context`는 Page 경로나 파일 소유 기록을 나타내는 짧은 문자열이다.
- 질의 결과 커서는 질의·분류·변경 번호·마지막 순위·내부 행 ID를 포함한다. 빈 질의는 마지막 수정일·행 ID를 포함한다. 다른 질의/분류·손상된 커서는 한국어 400을 반환한다.
- 커서 변경 번호가 현재 DB와 다르면 첫 페이지와 `reset: true`를 반환한다. 한 읽기 트랜잭션에서 변경 번호·결과·커서를 만든다.
- 관련성 검색은 FTS `MATCH`와 `ORDER BY rank`, 21개 조회로 다음 페이지 유무를 확인한다. 전체 결과 개수는 매 타자마다 집계하지 않는다.
- 결과 미리보기는 저장한 평문에서 최대 180 코드 포인트만 추출한다. HTML을 반환하지 않는다. Page 경로와 파일 이동 대상은 최대 20개 결과에 대해서만 현재 활성 기록에서 구한다.

## 검색창

- 모든 화면의 사이드바 검색·`⌘K`/`Ctrl+K`가 같은 팔레트를 연다. 열고 닫아도 작성 중인 메모/문서 초안을 유지한다.
- 기존 paper/forest·charcoal/sage 스타일을 계승한 Operate 화면이다. 작은 검색 입력, `전체·메모·페이지·파일·AI 요청` 분류, 결과의 출처와 짧은 본문, 더 보기를 제공한다.
- 200ms 입력 대기, AbortController, 요청 세대 번호로 이전 요청이 새 결과를 덮지 않게 한다. 한글 조합 중에는 요청과 Enter 이동을 보류한다.
- 검색·필터 변경 시 이전 결과/커서를 바로 비운다. 더 보기 중 입력/필터/변경 이벤트가 바뀌면 이전 응답을 무시한다. 휴지통/복원과 창 집중 후 현재 질의를 갱신한다.
- 방향키·Enter로 이동, Escape로 검색만 닫기, Tab 초점 가두기, 닫은 뒤 초점 복귀를 제공한다. 모바일 메뉴는 검색을 열 때 닫는다.
- 로딩·빈 결과·짧은 입력·조회 실패/재시도를 구분한다. 320px·390px·1327px, 두 화면 모드, 44px 조작 영역을 확인한다. 편집기나 Mermaid를 검색 의존성으로 불러오지 않는다.

## 성능과 검증

- 임시 DB의 1만·10만 건 혼합 자료에서 최초 색인 시간, 재시작 시간, 검색 p50/p95, 저장 시간, DB/색인 크기와 RSS를 측정한다. 희귀어·흔한어·두 글자·혼합 짧은어·없는어를 포함한다.
- 동일한 평문에서 문자열 전수 검색과 비교한다. 결과 동일성을 확인하며 특정 자료 크기의 시간을 N100 실측으로 표현하지 않는다.
- 현재 동기 SQLite 쿼리의 비용을 먼저 측정한다. 입력/저장을 점유하는 지연이 나오면 단일 검색 읽기 worker를 검토할 근거로 기록한다.
- Apple M1 Max·Node 24.18.0의 임시 10만 원본/10.2만 색인 자료에서 20개 조회 p95는 흔한 `여행` 49.711ms, `교토` 15.140ms, `교토 3` 19.005ms였다. v1의 혼합 조건 후보 본문 확인은 260.815ms여서 v2 문자 열로 교체했다. FTS는 77.16MiB → 104.50MiB, 전체 DB는 380.86MiB → 408.16MiB로 늘었다. 이 비용과 N100 미실측 범위를 함께 기록한다.
- 최종 자료의 저장 갱신 p95는 0.774ms, 정상 재시작은 29.591ms였다. 별도 새 읽기 프로세스 RSS는 유휴 79.70MiB, 검색 후 82.63MiB였다. 대량 생성 프로세스의 최대 RSS와 서비스 유휴 RSS는 분리해서 보고한다. HTTP·브라우저·N100 성능으로 환산하지 않는다.
- 저장소 테스트는 임시 디렉터리만 쓴다. 기존 기록 최초 이관, 재구축, 재시작, 중첩 표/링크, 유니코드, 긴 본문, 원자성, 휴지통/복원/첨부 가시성, 페이지 커서 리셋을 검증한다.
- Chrome QA는 지연·이전 응답·조합 입력·실패·더 보기·키보드·초안 보존·파일 이동과 화면 크기/모드를 검증한다. 기존 회귀 QA도 실행한다.
