# 입력함 자료를 페이지에 연결하는 설계

작성: 2026-09-27
상태: 2026-09-29 메모 → 기존/새 하위 페이지 가져오기·참조·첨부 재사용 구현. 블록 분배·공개 공유는 후속 단계. 현재 동작은 [`CURRENT_IMPLEMENTATION.md`](../../../CURRENT_IMPLEMENTATION.md)를 따른다.

## 2026-09-29: 메모 관리와 페이지 정리의 구분

최신 사용자 방향은 보관 목록을 `/memo`에서 관리하고 **AI 요청을 별도로 노출**하는 것이다. 하나의 임시 정리 문서를 반드시 거치는 흐름은 현재 진입 방식에서 제외한다. [메모 관리 규격](2026-09-29-memo-library-design.md)을 따른다.

- 메모는 제목 없는 `Capture` 원본이며 `/memo`에서 검색·열기·명시적 수정한다.
- AI 요청은 Capture에 연결된 당시 입력·템플릿·요청문 사본으로 `/memo?view=ai`에 보관한다. 실행 전이며 결과는 아직 없다.
- 페이지는 제목·블록을 가진 `Page`이며 `/pages/:id`에서 바로 편집한다. 메모를 거치지 않고 직접 쓸 수 있다.
- `/pages`·`/temp`의 이전 목록 주소는 `/memo`로 연결한다. 기존 임시 페이지는 일반 문서로 남고 새 임시 문서를 자동 생성하지 않는다.
- 원본을 페이지에 가져오기는 **구현**했다. 검토한 AI 결과 채택·선택 블록 분배는 **다음 구현**이다. 현재 샘플의 여행 페이지는 직접 작성한 예시이며 가져오기나 AI 실행 결과가 아니다.

후속 연결은 `/memo` 상세에서 필요한 내용과 출처를 선택한 기존 페이지 또는 새 하위 페이지에 담는 방식이다. 한 원본을 여러 페이지에서 활용하며 복사본의 편집은 원본을 바꾸지 않는다. 사용자가 일반 페이지를 정리 공간으로 쓸 수는 있지만 특별한 임시 역할을 요구하지 않는다. 페이지 간 블록 이동·복사는 별도 동작이고 이동을 택하면 대상 저장과 원본 블록 제거를 원자적으로 처리한다.

## 목적과 성공 기준

leneu의 가장 잦은 동작은 휴대폰이나 PC에서 메모·URL·스크린샷·파일을 즉시 보관하는 것이다. 이후 필요한 자료만 여행 일정이나 계획 페이지에 옮겨 정리한다. `Capture`는 사용자가 상세에서 직접 고칠 수 있고, 페이지에 복사한 글은 그와 독립적으로 바뀐다. 사용자가 요청하지 않은 OCR·요약·원격 AI 호출은 이 흐름에 끼어들지 않는다.

성공 기준은 다음과 같다.

1. 메모 상세에서 선택한 기존 페이지나 새 하위 페이지에 원본 참조·필요한 내용을 가져온다. 페이지 간 블록 이동·복사는 별도 후속 기능이며, 파일 업로드와 메모 저장의 기존 응답 경로는 느려지지 않는다.
2. 필요하면 원본 텍스트와 선택한 첨부를 페이지에 넣어 편집하거나 배치한다. 같은 입력을 여러 페이지에서 재사용해도 원본·파일 바이트를 복제하지 않는다.
3. 페이지를 다시 열거나 다른 기기에서 열어도 참조가 유지된다. 참조 대상이 없어지면 화면이 깨지지 않고 해당 블록만 안내한다.
4. 동시에 다른 탭에서 페이지를 고쳐도 기존 버전 충돌 보호가 유지된다. 네트워크 재시도로 같은 추가 작업이 중복되지 않는다.
5. 이 설계에서 생긴 비공개 참조나 파일이 나중에 공개 공유 페이지로 자동 유출되지 않는다.

## 선택한 접근

| 접근                        | 장점                                                        | 한계                                                     |
| --------------------------- | ----------------------------------------------------------- | -------------------------------------------------------- |
| 내용만 복사                 | 페이지에서 바로 편집 가능                                   | 원본과 관계가 끊기고 파일을 중복 저장하기 쉽다           |
| 원본만 참조                 | 원본 보존과 재사용이 단순                                   | 페이지 안에서 발췌문을 고칠 수 없다                      |
| **원본 참조 + 선택적 복사** | 출처를 남기면서 글을 자유롭게 편집하고 파일 바이트를 재사용 | 참조 블록과 복사한 글의 차이를 UI에서 명확히 보여야 한다 |

세 번째를 채택한다. 선택한 기존 페이지나 새 하위 페이지에 `Capture` 참조 블록을 넣는다. 사용자가 선택하면 참조 블록 다음에 원본 텍스트·URL의 편집 가능한 사본과 선택한 첨부 블록을 함께 추가한다. 복사한 글을 고치거나 지워도 메모 원문은 바뀌지 않는다. 복사문 자체에는 별도의 영구 출처 메타데이터를 붙이지 않는다. 출처가 필요한 경우 함께 추가된 참조 블록을 유지한다.

## 사용자 흐름

1. 입력함 항목 상세에 `내 페이지에 정리`를 둔다. 기존 저장 버튼·빠른 입력 도크에는 페이지 편집기 코드를 싣지 않는다.
2. 선택 창에서 기존 페이지의 제목 검색·계층 경로 또는 새 하위 페이지를 제공한다. 새 하위 페이지를 고르면 상위와 새 제목을 입력한다. 제목이 비면 `제목 없음`으로 만들고 이동 직후 제목에 초점을 둔다. 원본 참조는 기본 포함하고 `내용 복사`와 첨부별 `페이지에 넣기`를 고른다. 텍스트와 URL이 모두 없으면 내용 복사는 비활성이다.
3. 확인하면 서버가 선택한 기존 페이지 끝에 블록을 한 번의 작업으로 추가하거나, 선택한 새 하위 페이지와 내용을 함께 만든다. 성공 후 해당 페이지로 이동하고 새 블록 위치를 보여준다. 실패하면 창과 선택 상태를 유지하고 이유를 표시한다.
4. `원본 참조` 블록은 유형, 한국 시간, 한 줄 미리보기, 첨부 수를 보여주고 누르면 개인용 입력함 상세를 연다. `/captures/:id` 경로는 기존 상세 패널을 ID로 직접 열고 새로고침 뒤에도 유지한다. 입력함 항목에는 이미 연결된 페이지 목록을 볼 수 있다. 첫 구현에서 페이지 안의 `/` 메뉴로 기존 입력을 찾는 기능은 범위에 넣지 않는다.
5. `내용 복사`는 일반 편집 블록을 만든다. 줄바꿈을 보존하되 원문을 임의로 Markdown 명령으로 해석하지 않는다. URL은 일반 링크로 넣는다. 이미지는 원본 `Asset` ID를 가리키는 이미지 블록, 그 밖의 파일은 파일 블록으로 넣는다.

모바일 선택 창은 검색과 확인 버튼을 엄지로 누르기 쉬운 영역에 둔다. 저장 중 중복 제출을 막고, 성공 확인은 짧게 보여준다. 선택 창을 열 때만 페이지 검색 코드를 불러온다.

## 저장 계약

기존 `Page.document` 블록 JSON이 기준 데이터다. `schemaVersion: 1`에 다음 블록 유형을 추가하고 서버에서 속성과 크기를 검증한다.

| 블록           | 저장 속성            | 동작                                                                                |
| -------------- | -------------------- | ----------------------------------------------------------------------------------- |
| `captureRef`   | `captureId`          | 개인용 화면에서 원본을 조회하는 카드. 본문 텍스트·파일 URL은 JSON에 복제하지 않음   |
| `asset`        | `assetId`, 표시 형태 | 기존 파일 바이트를 재사용하는 이미지·파일 블록. 저장 키·디스크 경로를 저장하지 않음 |
| 일반 문단·링크 | 현재 블록 형식       | 사용자가 선택한 편집 가능한 사본                                                    |

`PageReference(page_id, block_id, target_type, target_id)`를 새 파생 테이블로 둔다. `target_type`은 우선 `capture`, `asset`, `page`다. 서버는 페이지 생성·수정·가져오기와 같은 트랜잭션 안에서 문서를 검증하고 참조 행을 다시 만든다. 기존 페이지 문서도 마이그레이션에서 스캔해 `page` 링크를 색인한다. 참조 행은 문서에서 재구축 가능하므로 문서와 어긋난 상태를 복구할 수 있다.

서버는 추가 작업에서 `captureRef.captureId`의 존재, `asset.assetId`의 존재와 해당 입력과의 소속을 검증한다. 일반 페이지 저장에서는 모든 참조 ID 형식과 새로 생긴 참조의 대상 존재를 확인한다. 이미 저장돼 있던 참조의 대상이 사라졌다면 해당 블록을 `찾을 수 없는 원본`으로 표시하고 다른 글의 저장은 허용한다. 현재 `assets.capture_id`는 원본 입력에 종속돼 있으므로, 파일을 참조하는 페이지가 있을 때 향후 입력 삭제가 파일을 지우지 못하도록 삭제 정책을 정한다. 현재는 입력·페이지 삭제 API가 없으며 이 설계에서 삭제 기능을 추가하지 않는다.

Markdown은 여전히 편집기의 저장 형식이 아니다. `Markdown 보기·복사`는 참조·첨부 블록을 조용히 생략하지 않고 읽을 수 있는 설명과 앱 전용 ID를 텍스트로 내보낸다. 이 텍스트만 다른 앱에 붙여넣어도 원본 파일 바이트가 따라가지 않는다는 안내를 표시한다. 완전한 이동과 복원은 후속 Markdown+첨부 묶음 내보내기 또는 전체 백업에서 처리한다.

## API와 동시 편집

- `GET /api/pages/search?q=&cursor=`: 선택 창의 서버 측 제목 검색. 현재 `GET /api/pages`의 200개 제한에 막히지 않으며 결과를 페이지 단위로 반환한다.
- `POST /api/pages/:id/capture-imports`: `{ operationId, captureId, copyContent, assetIds }`를 받아 기존 페이지 끝에 추가한다.
- `POST /api/pages`의 새 페이지 생성 경로: `parentId`와 선택적 `captureImport`를 받아 상위 존재 확인·하위 페이지 생성·블록 추가를 한 트랜잭션으로 처리한다. `captureImport`의 `operationId`는 생성까지 포함해 중복을 막는다. 기존 요청 형식은 계속 허용한다.
- 입력함 상세에서 연결된 페이지 목록은 `PageReference`로 조회한다. 본문 전체를 읽어 매번 탐색하지 않는다.

이 경로들은 본인용 API에만 등록한다. 현재 개발 서버에는 인증이 없으므로 공개 주소에 연결하지 않는다. 후속 공유 서비스에는 검색·가져오기·입력함 조회 경로를 등록하지 않는다.

`operationId`는 제출 시 만든 UUID다. 서버는 작업 ID·요청 내용·대상 페이지를 기록해 같은 요청의 재시도에는 같은 결과를 돌려주고 블록을 다시 넣지 않는다. 같은 ID에 다른 내용을 보내면 충돌 오류를 돌려준다. 페이지를 찾지 못하거나 원본·선택 파일이 없으면 변경 없이 404/검증 오류를 돌려준다. 문서의 1MB·1,000블록 한도를 넘으면 전체 작업을 취소한다.

가져오기 API는 서버 트랜잭션에서 최신 문서를 읽고 끝에 추가한 뒤 `version`을 올린다. 이미 열린 다른 탭의 저장은 기존 `expectedVersion` 검사에서 409가 되며 로컬 초안 복구 흐름을 유지한다. `PageReference` 갱신과 문서·버전 갱신도 같은 트랜잭션에 넣는다. 새 페이지 생성 도중 실패하면 빈 페이지만 남기지 않는다.

## 공개 공유와 AI의 경계

`captureRef`에는 비공개 원본이 들어 있으므로 공개 공유 렌더러는 해당 블록을 건너뛰고 `Capture` API를 호출하지 않는다. 사용자가 페이지에 복사한 일반 글은 페이지 본문이므로 향후 그 페이지를 공유하면 공개 범위에 들어간다. 첨부는 페이지에 보이더라도 `ShareGrant`가 해당 `assetId`를 허용한 경우에만 공개 파일 경로를 발급한다. 이미 공유 중인 페이지에 새 파일을 넣어도 공유 허용 목록에 자동 추가하지 않는다. 내부 페이지 링크도 대상 페이지의 공유 권한을 따로 검사한다.

이 단계에서 OCR·요약·조사는 실행하지 않는다. 후속 `DerivedContent`는 사용자가 채택할 때 같은 페이지 추가 경로를 재사용하고, 결과와 원본의 출처를 별도로 기록한다.

## 선행 안정화와 범위

이 연결 기능에 앞서 페이지 이동의 존재하지 않는 `parentId` 허용을 막는다. UI가 페이지 계층의 깊이 8 이후를 숨기는 문제와 목록 200개 이후를 조용히 생략하는 문제도 없앤다. 페이지 선택 창과 사이드바는 유효한 페이지를 찾을 수 있어야 한다. 이 수정은 데이터 손실 방지와 대상 선택의 전제다.

이번 단계에는 페이지 직접 업로드, 삭제·휴지통, 페이지 변경 이력, 본문 통합 검색, OCR·AI 실행, 공개 공유 서버를 넣지 않는다. 직접 업로드는 `Asset`의 소유 관계를 독립시키는 후속 단계에서 다룬다. 다만 이번 `asset` 블록과 `PageReference` 계약은 그 단계에서도 유지한다.

## 검증 시나리오

1. 메모·URL·이미지·일반 파일 입력을 각각 기존 페이지와 새 페이지에 추가한다. 입력함 원문과 파일 바이트는 변하지 않는다.
2. 같은 입력을 두 페이지에 참조하고, 한쪽의 복사문을 고친 뒤 다른 쪽과 원본을 다시 확인한다.
3. 일부 파일만 선택해 페이지에 넣고 다시 연다. 선택하지 않은 파일은 페이지에 나타나지 않는다.
4. 요청 응답을 잃었다고 가정해 같은 `operationId`로 다시 제출해도 블록이 하나만 생긴다. 한도가 넘거나 파일이 다른 입력에 속하면 페이지와 참조 행 모두 바뀌지 않는다.
5. 다른 탭에 열린 페이지가 있는 동안 입력을 추가한다. 오래된 탭의 저장이 409를 받고 초안을 보존한다.
6. 200개를 넘는 페이지와 깊은 하위 페이지도 선택 창·사이드바에서 찾을 수 있다. 없는 상위 ID로 이동을 요청하면 거절된다.
7. 공유 렌더러를 구현할 때 비공개 참조 내용·파일 주소가 응답에 없고, 허용되지 않은 파일을 요청해도 거절되는 시나리오를 필수 검증으로 삼는다.
8. 선택한 상위 아래에 새 페이지가 나타나고 바로 편집할 수 있다. 생성 중 응답을 잃어 재시도해도 자식은 하나이며, 상위 본문과 입력함 원문은 유지된다. 대상 변경 뒤 재시도는 이전 작업의 상위 ID를 몰래 바꾸지 않는다.

## 이어지는 작업 순서

1. 페이지 계층 검증과 목록 누락 수정.
2. 블록·`PageReference`·가져오기 API와 트랜잭션.
3. 입력함 상세의 페이지 선택 창, 참조·첨부 렌더링, 모바일 검증.
4. 통합 검색의 색인 및 한국어 질의 검증.
5. 사용자 요청으로 시작하는 AI 작업과 결과 채택.
6. 별도 읽기 전용 공유 서비스, 파일 허용 목록, 백업·미니PC 이전.
