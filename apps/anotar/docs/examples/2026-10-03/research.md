개인 작업 공간에서 가장 중요한 것은 방금 쓴 글이 남아 있는지 알 수 있는 것이다. leneu의 저장 흐름을 살펴보니, **기기에 저장됐다는 표시와 서버에 반영됐다는 표시를 구분하는 것**이 오프라인 사용의 출발점이었다.

## 핵심 질문

지하철에서 휴대폰으로 메모를 쓰고, 집에 돌아와 PC에서 이어서 정리하려면 어떤 저장 기준이 필요한가? 이번 검토는 메모·페이지·첨부의 보관과 재연결에 집중한다. 여러 사람이 동시에 한 문장을 편집하는 협업 기능은 후속 검토 대상이다.

읽는 사람은 이 문서에서 세 가지를 판단하면 된다. 지금 글이 어디에 남아 있는지, 다른 기기에서 언제 볼 수 있는지, 충돌했을 때 무엇을 보존하는지다.

## 요약과 결론

**기기에 먼저 저장하고 서버로 전송하는 현재 방향을 유지한다.** 단, ‘저장 완료’ 하나로 모든 상태를 표현하면 사용자가 실제로 확인한 범위보다 더 많은 것을 보장한 것처럼 보인다.

| 화면 표시 | 확인한 것 | 다음에 할 일 |
| --- | --- | --- |
| 기기에 저장됨 | 이 브라우저의 저장소에 원문이 남음 | 서버 반영을 기다림 |
| 동기화 완료 | 대기 중인 변경이 서버에 반영됨 | 다른 기기에서 최신 글 확인 |
| 변경 확인 필요 | 서로 다른 편집 또는 서버 변경이 있음 | 두 사본을 비교하고 반영 방법 선택 |
| 기기에 저장하지 못함 | 원문 보관이 실패함 | 입력을 복사하고 저장 문제 해결 |

판단 기준은 단순하다. 작성자는 네트워크를 기다리지 않고 기록할 수 있어야 한다. 다른 기기로 넘어갈 때에는 서버 반영 여부를 확인할 수 있어야 한다. 충돌은 어느 글도 조용히 지우지 않는 방식으로 다룬다.

## 근거와 발견

### 메모와 페이지는 다른 속도로 다뤄야 한다

메모는 저장 버튼을 누르면 기기 원문·첨부의 저장을 확인한 뒤 입력란을 비운다. 페이지는 타이핑을 계속하므로 마지막 입력 후 약 250ms에 기기 저장을 시도하고, 약 750ms에 전송할 사본을 준비한다. 이 값은 현재 구현의 대기 시간이며 모든 기기의 응답 속도를 뜻하지 않는다.

따라서 페이지 입력 직후 앱을 강제 종료하는 상황까지 ‘무조건 저장된다’고 표현할 수는 없다. 화면 이탈 시 저장 시도를 하는 것과, 운영체제가 프로세스를 즉시 끝내는 것은 다른 조건이다.

### 오프라인에서 보이는 자료에는 범위가 있다

앱을 한 번 열었다고 모든 페이지와 첨부가 기기에 내려오는 것은 아니다. 필요한 페이지는 미리 열거나 오프라인 보관하고, 설정의 기기 저장소에서 첨부까지 준비됐는지 확인해야 한다. 다른 주소·포트·브라우저 프로필은 별도의 저장소다.

서버 백업도 휴대폰 안의 미전송 원문을 포함하지 않는다. 서버 백업과 기기 대기 자료 내보내기는 서로 다른 복구 수단으로 안내해야 한다.

### 충돌 보존은 복구 동작까지 검증해야 한다

오프라인 최종 리뷰에서는 같은 브라우저의 두 탭이 서로 덮는 경우, 취소한 요청이 다시 전송되는 경우, 복구 과정에서 하위 페이지와 첨부가 빠지는 경우를 발견하고 수정했다. ‘양쪽 사본을 보존한다’는 설계 문구만으로 충분하지 않았고 실제 재현이 필요했다.

2026년 10월 3일의 문서 작성 흐름 검증에서는 오프라인 템플릿 생성·재열람·재연결과 자료 발췌 삽입을 Chrome에서 확인했다. 실제 휴대폰의 앱 종료·저장소 정리·네트워크 전환까지 입증한 것은 아니다.

## 남은 질문

1. 실제 휴대폰에서 입력 직후 앱을 종료하면 어디까지 남는가? ‘기기에 저장됨’을 확인한 경우와 확인하지 않은 경우를 나눠 시험해야 한다.
2. 오래 보관한 페이지의 첨부가 누락되면 사용자가 쉽게 알아차리는가? 부분 보관 표시와 재시도 흐름을 실제 사용으로 확인해야 한다.
3. 기기 저장 후 전송 준비 전의 짧은 구간에서 전역 동기화 상태가 충분히 명확한가? 원문 보존과 상태 표시의 정확성을 함께 확인해야 한다.

다음 검토는 기능 수를 늘리는 것보다 **메모 하나를 작성하고, 연결을 끊고, 다시 열고, PC에서 찾는 과정**을 실제 기기에서 반복하는 데 둔다.
